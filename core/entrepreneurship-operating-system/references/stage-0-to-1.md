# 0→1 参考框架

## 当前状态

- 状态：初始版
- 适用阶段：想法、原型、MVP、首批客户
- 更新时间：2026-10-11

## 0→1 的目标

不是“做出产品”，而是证明一个可重复的最小商业闭环：

```text
明确问题 -> 明确买家 -> 最小可信结果 -> 真实使用 -> 真实付费 -> 重复发生
```

## 最小证据阶梯

1. 用户承认问题，并能描述最近一次发生。
2. 用户展示当前替代方案和真实输入。
3. 用户愿意提供样本、时间或访问权限。
4. 用户使用原型或手工服务完成任务。
5. 用户将结果放入真实工作流。
6. 用户付费或进入明确采购流程。
7. 用户重复使用并愿意续费/推荐。

不要跳过前面的证据，直接用“市场很大”推断后面的证据。

## 0→1 周期复盘

每周记录：

- 本周验证的假设。
- 观察到的行为证据。
- 被推翻的假设。
- 客户原话和实际行为的差异。
- 哪个功能被砍掉。
- 下一周唯一最重要的实验。

## 企业行动依赖检查

企业客户认可价值，不等于会购买和落地。先画出客户必须完成的行动链：

```text
老板认可 -> 预算批准 -> champion 推动 -> 跨部门协同
-> 数据/权限提供 -> 流程改变 -> 员工使用 -> 结果产生
```

行动链越长，越依赖客户内部权力结构，外部创业者越难控制结果。

在做企业级 SaaS 或解决方案前，必须确认：

- 有预算所有者。
- 有真实内部 champion。
- 有能拍板的决策者。
- 有试点范围、截止日期和责任人。
- 客户愿意提供数据、权限和反馈。
- 首个价值不需要全公司统一行动才能出现。

出现以下情况，默认缩小为个人/团队工具、结果型服务或数据 API：

- 只有“老板觉得不错”，但没有老板参与或预算。
- 需要多个部门配合，但没有项目负责人。
- 需要改变组织流程，但没有强制事件或截止时间。
- 创始人必须长期驻场、培训、协调和催促才能交付。

澹墨质量没有形成购买，不应只归因于功能、宣传或价格。更深层的可能性是：它要求客户内部老板推动质量流程、跨部门协作和组织行动，而产品方作为外部团队无法控制这些关键变量。这个教训应进入所有企业产品的进入闸门。

## 域名与定位容错

域名选择是 0→1 的可逆性决策，不应只按“看起来专业”判断。

### 精准域名的收益

- 第一眼解释成本低。
- 适合已经验证的垂直品牌。
- 可能帮助特定关键词的记忆和传播。

### 精准域名的代价

- 把未验证的市场假设写入长期资产。
- 文章、SEO、反向链接、截图、邮件和客户记忆都绑定到旧定位。
- API Base URL、OAuth 回调、支付 Webhook 和白名单迁移成本高。
- 需求转向时容易出现“已经投入这么多，不能放弃”的沉没成本偏差。

### 0→1 域名规则

1. 未验证付费和留存前，优先选择能力层域名，例如 `data`、`platform` 或品牌名。
2. 具体垂直场景放在路径中，例如 `/trade-rules`、`/us-tariffs`，而不是直接写死在主域名。
3. 如果使用精准域名，保留宽泛母域名和迁移计划；不要让 API、登录回调和支付配置只依赖精准域名。
4. 定位实验优先使用 landing page、子路径、子域名和内容主题测试，不要每次试错都换主域名。
5. 发布前建立迁移清单：canonical、301、DNS、证书、CORS、OAuth、Webhook、API Base URL、文档链接、邮件模板和客户通知。

### 例子

假设一个过窄的合规域名代表“合规数据产品”，但后续发现更大的机会是“结构化贸易数据 API”，合理路径不是下架全部文章或继续硬撑，而是：

```text
data.danmo.tech                    # 稳定能力层入口
data.danmo.tech/trade-rules         # 关税和贸易措施
data.danmo.tech/sanctions           # 未来可能的制裁数据
data.danmo.tech/regulatory          # 未来可能的监管数据
```

原有文章保留为历史内容，通过 301、canonical 和页面说明迁移到新路径。除非旧域名本身造成严重信任或法律问题，否则不要因为定位转向就删除已积累的内容资产。

域名宽泛不等于产品模糊：主域名可以宽，首屏定位、API 套餐和客户案例必须窄。
