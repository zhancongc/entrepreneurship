# 服务驱动的 0→1 创业路径

## 文档信息

- 状态：当前有效的 0→1 参考框架
- 适用对象：个人公司、B2B、专业服务、数据服务、AI 辅助交付
- 核心路径：服务获客 → 客户反馈 → 标准化交付 → 交付提效 → 渐进产品化

## 核心认知

对于不会或不想依赖广告、SEO、内容增长的创业者，服务可以同时承担三件事：

```text
服务获客
-> 直接接触有真实问题的买家
-> 收到真实现金和行为反馈
-> 积累案例、流程、判断和信任
```

这条路径比“先做工具，再寻找用户”更适合问题复杂、信任要求高、交付结果比软件功能更重要的场景。

但它不是“服务天然免费营销”，而是用创始人的时间、交付能力和客户成功替代现金营销预算。成本从广告费转移成了人工成本和机会成本。

## 为什么服务适合 0→1

### 服务是带着收入的问题验证

客户愿意付费、提供真实资料、接受交付并再次购买，都是强于口头访谈的证据。

需要区分：

- “客户愿意买一次服务”证明有人愿意为结果付费。
- “多个客户反复购买相似服务”证明问题有重复性。
- “客户愿意使用标准化版本”才证明存在产品化机会。

一次高价定制单不能直接证明 SaaS、API 或自助工具需求。

### 服务是带着反馈的调研

服务交付会暴露：

- 客户真正卡在哪里。
- 客户当前使用什么替代方案。
- 哪些步骤最耗时。
- 哪些判断最有价值。
- 哪些错误最昂贵。
- 哪些结果客户愿意付更多钱购买。

但必须记录实际行为和交付数据，不能只凭创始人的印象总结需求。

### 服务是带着现金流的长期主义

服务收入可以支付早期生活和开发成本，减少融资压力，并给创始人时间验证产品。但服务也可能吞噬全部时间，因此必须从第一单开始记录交付工时和毛利。

## 服务产品化不是自动变成软件

复杂服务的价值通常不在“写字”或“调用 AI”，而在：

- 诊断问题。
- 判断优先级。
- 选择策略。
- 处理例外。
- 承担结果责任。
- 复核质量。

因此产品化有三种形态，不能默认只有 SaaS：

### 1. 内部交付系统

工具只给服务方使用，用来提高自己的交付速度和质量。客户继续购买服务。

适合：判断复杂、客户不愿学习、结果责任较高的场景。

### 2. 服务产品化

把服务拆成固定套餐、标准输入、标准流程、标准交付物和标准价格。仍然卖服务，但边际交付成本下降。

适合：需求相似但仍需要人工判断的场景。

### 3. 自助产品

客户自己完成流程，软件承担主要价值交付。只有当客户能够独立完成关键任务时，才适合走这条路。

适合：输入稳定、规则清晰、风险可控、客户有意愿自己操作的场景。

推荐顺序通常是：

```text
内部交付系统
-> 服务产品化
-> 人工审核的半自助产品
-> 完全自助产品
```

## 护城河不应是“我会用 AI”

AI 工具使用能力会快速普及。长期资产应沉淀为：

- 真实案例库。
- 领域判断规则。
- 客户场景和异常处理经验。
- 标准化工作流。
- 质量检查清单。
- 交付数据和结果反馈。
- 客户关系和信任。
- 可迁移的内部工具和数据资产。

其中案例、客户数据和交付结果必须注意隐私、授权、商业秘密和再利用边界，不能默认把客户交付物训练成公开资产。

## 推荐落地步骤

### Step 1：先做 3–5 个付费单

不要先开发完整工具。选择一个明确垂直场景，完成少量真实交付，并记录：

- 客户来源。
- 购买者和使用者。
- 交付输入。
- 每个环节耗时。
- 客户最常问的问题。
- 客户最不满意的地方。
- 返工原因。
- 交付结果。
- 客户是否再次购买或推荐。

### Step 2：建立交付账本

每个项目至少记录：

```text
客户收入
- 人工时间成本
- 外部数据/工具成本
- 沟通和售后成本
= 项目贡献毛利
```

没有交付毛利数据，就不知道应该提价、砍范围、自动化还是停止。

### Step 3：识别重复任务

把交付拆成：

- 每次都重复的任务。
- 需要领域判断的任务。
- 只有少数客户需要的任务。
- 高风险、必须人工审核的任务。

优先自动化重复且低风险的部分，不要先自动化最复杂、最需要责任承担的判断。

### Step 4：标准化服务

建立：

- 套餐。
- 输入表单。
- 交付流程。
- 模板库。
- 质量清单。
- 交付 SLA。
- 变更和返工规则。
- 价格和紧急费。

标准化的目标是让下一单更快、更稳、更容易交接，而不是制造一个看起来像软件的页面。

### Step 5：用内部工具提效

先为自己开发：

- 数据检索。
- 模板匹配。
- 初稿生成。
- 格式检查。
- 规则检查。
- 版本比较。
- 交付记录。

内部工具必须测量节省了多少时间、降低了多少错误，而不是以代码量衡量进展。

### Step 6：用客户行为决定产品化形态

判断规则：

| 观察到的事实 | 更可能的方向 |
| --- | --- |
| 客户只购买你的判断 | 高级人工服务或专家审核 |
| 客户输入和需求高度重复 | 服务套餐或半自动产品 |
| 客户愿意自己操作 | 自助工具 |
| 多个客户需要同一数据资产 | API/数据产品 |
| 客户只在紧急事件发生时购买 | 项目制服务或事件型产品 |
| 交付高度依赖行业关系 | 垂直服务和关系型销售 |

## 关键陷阱

### 企业行动依赖陷阱

有些企业服务或 SaaS 的价值必须等客户老板推动组织行动后才会出现，例如跨部门质量流程、全公司数据治理、供应商协同和组织级整改。早期创业者很难控制客户内部的预算、权限、政治和执行。

除非客户明确提供预算所有者、内部 champion、决策者、试点责任人、数据权限、时间表和验收标准，否则默认不做这类企业行动型 SaaS。优先缩小为单角色工具、单团队工作流、结果型服务或数据 API。

### 服务收入不等于产品需求

客户可能愿意为“你亲自处理”付费，却不愿意为工具或 API 付费。必须单独验证：

- 客户是否愿意使用标准版本。
- 客户是否愿意减少人工接触。
- 客户是否愿意按订阅或调用量付费。

### 转介绍不等于零获客成本

转介绍需要交付质量、主动请求、跟进机制和客户信任。仍然要记录：

- 每个渠道带来的客户数。
- 成交率。
- 交付成本。
- 续费率。
- 转介绍率。

### 服务会把创业者锁死

危险信号：

- 收入增加但空闲时间减少。
- 每个客户都要求独立定制。
- 没有任何交付步骤被标准化。
- 创始人不参与就无法交付。
- 内部工具只增加复杂度，没有节省时间。

出现这些信号时，应提价、缩小客户范围、砍掉例外，或停止产品化幻想，而不是继续加功能。

### AI 提效可能掩盖质量风险

AI 生成内容不等于领域判断正确。高风险服务必须保留：

- 人工审核。
- 来源证据。
- 版本记录。
- 客户确认。
- 错误修正流程。

## 阶段闸门

### 进入服务产品化

- 至少 3 个客户购买相似服务。
- 交付流程中有明显重复步骤。
- 能计算每单毛利和交付时间。
- 标准化不会明显降低结果质量。

### 进入半自助产品

- 客户愿意自己完成部分流程。
- 输入格式相对稳定。
- 人工审核可以覆盖高风险判断。
- 客户愿意为标准化版本支付。

### 进入纯产品/API

- 多个客户有相似的结构化需求。
- 客户愿意脱离创始人直接使用。
- 结果质量可以自动或半自动验证。
- 支持成本不会随客户线性增长。

## 对数据产品的映射

对于贸易数据 API，可以把服务模式理解为：

```text
人工帮客户整理/解释贸易规则
-> 收集真实 HTS、原产国和日期样本
-> 发现客户真正需要的字段和变化
-> 标准化数据采集和验证
-> 先提供人工辅助 API 接入
-> 再提供可自助消费的数据 API
```

如果客户不愿意购买原始数据 API，但愿意购买“规则解释、编码覆盖和异常处理”，这不是失败，而是说明产品化形态可能应先是专家辅助数据服务。

## 最终原则

```text
服务获客
-> 用现金验证问题
-> 用交付积累判断和数据资产
-> 用标准化降低交付成本
-> 用内部工具提高效率
-> 用客户行为决定产品化形态
-> 用口碑和复购验证可重复性
```

这条路径最适合 0→1，但必须持续检查：服务是在帮助你接近可复制产品，还是只是把你变成更忙的自由职业者。
