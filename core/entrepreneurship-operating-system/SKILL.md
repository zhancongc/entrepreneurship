# 创业操作系统

这是一个主题 Skill，不模拟某个创业者的语气。它的任务是把创业从“想法和功能”转换成一组可以被验证、被证伪、被复用的商业假设。

对于个人公司、B2B、专业服务、数据服务和 AI 辅助交付，默认额外检查一条路径：**服务获客 → 客户反馈 → 标准化交付 → 交付提效 → 渐进产品化**。这条路径不是所有创业项目的答案，也不能把一次服务收入误判为软件或 API 需求。

## 核心原则

1. 先验证问题和付费，再扩大方案和工程投入。
2. MVP 验证的是持续使用和真实付费，不是代码能运行。
3. Discovery 与 Delivery 双轨并行，而不是需求收集完再开发。
4. 指标必须指向用户获得的价值，不能用注册数和调用量掩盖没有价值。
5. 数据、支付和信任是产品的一部分，不是上线后的附属工作。
6. 在不确定性最大时保持可逆；在证据足够时集中资源。
7. 复用抽象来自第二个真实案例，不来自想象中的未来。
8. 习惯化不等于每天使用；对 SaaS 更准确的判断是“重复触发 + 不可替代性”。
9. 产品筛选必须同时看真需求、重复触发、付费意愿、信任、获客效率和单位经济。
10. 一人公司优先选择在高价值时刻必需的专业工具，不追逐大众产品的日活和注意力。
11. 商业价值要看支付能力与需求刚性：高预算客户的大客单，或低预算用户的高频小额刚需，都可能成立；低预算用户的非刚需和高预算客户的低价值小单，通常都不适合优先做。

## 适用范围

- 个人创业、独立开发、B2B SaaS、API 产品、数据产品和工具型产品。
- 从模糊点子到首批客户、首笔收入和可重复交付。
- 需要判断继续、转向、缩小范围或停止的创业项目。

## 不适用范围

- 不能替代法律、税务、会计、金融或行业合规意见。
- 不能凭空证明市场规模、客户需求或 PMF。
- 不能用“增长技巧”补救没有真实问题的产品。
- 不建议在没有证据时输出精确收入预测。

## 阶段路由

先判断项目处在哪个阶段：

| 阶段 | 核心问题 | 默认产出 |
| --- | --- | --- |
| 0→1 | 是否有真实问题、明确买家和首个可售解法？ | 假设栈、客户证据、MVP、首笔收入 |
| 1→10 | 首批客户是否能重复获取、交付和续费？ | 可重复销售、激活、留存和交付流程 |
| 10→100 | 增长是否可以规模化而不摧毁质量和现金流？ | 组织、渠道、自动化、单位经济和治理 |

默认聚焦 0→1。除非用户明确进入后续阶段，不要提前输出规模化方案。

## 六维产品筛选

对一个新产品先做六维评估：

```text
真需求 × 重复触发 × 付费意愿 × 信任 × 获客效率 × 单位经济
```

前三项回答“有没有生意”，后三项回答“这个生意是否适合当前创业者”。任意一项极弱，都不应靠增加功能掩盖。

### 六个维度

- **真需求**：用户是否正在为问题付出时间、金钱、风险或机会成本。
- **重复触发**：问题是否会再次发生，触发可能是每日、每周、每月、项目、变更、审计或异常事件。
- **付费意愿**：是否有预算、真实付款、采购流程或明确的结果价值。
- **信任**：用户是否敢把关键任务、数据或决策交给产品。
- **获客效率**：能否以创始人可承受的时间和现金成本找到目标客户。
- **单位经济**：单个客户收入是否覆盖数据、API、交付、支持、支付和获客成本，并留下合理利润。

### 重复触发类型

不要只问“用户每天用不用”，应识别产品属于哪种持续价值：

1. **Daily Habit**：每天高频使用，低摩擦。
2. **Monitoring Habit**：持续监控，异常或变化触发行动。
3. **Workflow Habit**：项目、变更或任务启动时进入工作流，并沉淀历史数据。
4. **High-Stakes Tool**：低频但高风险、高客单价，关键时刻必须可靠。

一人公司通常更适合第 2、3、4 类，而不是和大众产品竞争每日注意力。

### 一人公司筛选问题

- 是否有一个足够窄且可直接触达的买家群体？
- 客户是否可以由一个人或一个团队独立购买和使用？
- 是否不依赖客户老板推动长期组织变革？
- 是否能通过服务、内容、关系或定向外联获客？
- 客单价是否足以覆盖创始人的销售和支持时间？
- 产品是否能沉淀数据、配置、历史或工作成果，提高不可替代性？

详细评估模板见 `references/product-selection.md`。

## 工作流

### Step 1：识别阶段和事实

先问或明确以下事实：

- 产品是什么，谁付费，谁使用，谁承担风险？
- 用户现在如何完成这件事？替代方案是什么？
- 问题多久发生一次，当前成本是什么？
- 已有客户、访谈、试用、付费或留存证据是什么？
- 当前是想法、原型、MVP、试点还是已有收入？
- 哪些数据是事实，哪些只是推测？

如果用户已经提供足够事实，不重复提问；直接列出不确定性。

### Step 2：建立假设栈

把愿景拆成可证伪的“如果……那么……”：

1. **问题假设**：目标用户确实反复遇到该问题。
2. **买家假设**：存在有预算、有权力或能推动购买的人。
3. **价值假设**：解决问题后，价值大于切换和支付成本。
4. **方案假设**：最小方案足以让用户完成关键任务。
5. **渠道假设**：可以通过可承受成本触达客户。
6. **留存假设**：问题会重复发生，产品会嵌入工作流。
7. **信任假设**：客户愿意把关键数据、流程或决策交给产品。
8. **经济假设**：价格、毛利、支持成本和获客成本能形成可持续模型。

每个假设必须包含：证据、未知点、最小实验、通过标准、失败后的动作和截止日期。

### Step 3：选择最贵的未知数

不要按功能列表排期。优先验证同时满足以下条件的假设：

- 若为假，会使整个项目失去意义。
- 当前证据最弱。
- 可以用低成本实验快速验证。
- 结果会改变下一步决策。

默认优先级通常是：问题真实性 > 付费意愿 > 首次价值 > 持续使用 > 可重复获客 > 扩展工程。

### Step 4：设计实验

实验必须连接到行为，而不是态度：

| 假设 | 弱证据 | 强证据 |
| --- | --- | --- |
| 用户有痛点 | “听起来不错” | 用户展示当前流程并提供真实样例 |
| 用户需要产品 | 愿意注册 | 愿意接入、迁移或提供数据 |
| 用户愿意付费 | 说可以付费 | 真实付款、采购单或试点合同 |
| 用户会留存 | 使用一次 | 在真实工作流中重复调用/续费 |
| 数据有价值 | 页面浏览 | 结果进入客户生产或决策流程 |

实验设计应尽量短：访谈、手工服务、可点击原型、单端点 API、限定数据集、预售或付费试点都可以是 MVP。先验证价值，再自动化交付。

### Step 5：双轨执行

**Discovery** 负责下一个问题：访谈、观察、原型测试、价格实验、数据分析和证伪。

**Delivery** 负责当前已验证的最小方案：代码、测试、部署、监控、数据质量和客户交付。

每个迭代周期结束时必须回答：

- 哪个假设被强化？
- 哪个假设被削弱或证伪？
- 哪个行为证据改变了优先级？
- 下个周期最值得验证的未知数是什么？
- 哪些工作应停止，而不是继续完善？

### Step 6：用指标而非感觉决策

先定义北极星行为：用户真正获得核心价值的可观测动作。

适合 API/数据产品的例子：

> 每周成功完成真实业务查询的付费生产集成数。

不要把注册数、页面浏览、API 总调用量、创建 Key 数量直接当作价值指标。

辅助指标：

- 从注册到首次成功请求的时间。
- 从首次请求到生产集成的转化率。
- 免费到付费转化率。
- 付费组织周留存和续费率。
- 每个组织每周有效业务请求数。
- 数据错误率、修正时间和发布延迟。
- 支付成功率、退款率和支持成本。

### Step 7：阶段闸门

每个阶段只在证据达到标准后前进：

| 闸门 | 通过信号 | 未通过动作 |
| --- | --- | --- |
| 问题闸门 | 用户展示真实、反复、昂贵的问题 | 缩小人群或换问题 |
| 价值闸门 | 用户完成关键任务并愿意继续使用 | 改方案或停止 |
| 付费闸门 | 至少有真实付费或正式采购意愿 | 改买家、定价或价值主张 |
| 留存闸门 | 用户在真实流程中重复使用 | 找到触发机制或停止扩张 |
| 复现闸门 | 不依赖创始人手工推动也能成交/交付 | 优化渠道和流程 |
| 规模闸门 | 单位经济、质量和现金流可控 | 先修复基础，不扩大规模 |

## 0→1 深度框架

### 1. 问题不是“有人喜欢”，而是“有人正在付出代价”

优先观察用户已经投入的代价：人工维护、重复复制、错误损失、等待、合规风险、收入损失、内部协调和替代工具费用。

### 2. 买家、使用者和受益者可能不同

必须分别识别：谁每天使用、谁批准预算、谁承担错误、谁从结果中受益。只访谈使用者而不触及购买链，会高估需求。

### 3. MVP 是最小可信闭环

MVP 不等于功能最少，而是从触发到价值兑现的最短完整路径：

```text
真实问题
-> 用户输入
-> 最小处理
-> 可验证结果
-> 进入真实工作流
-> 用户愿意继续/付费
```

### 4. 数据产品先卖“确定性”

如果产品涉及规则、贸易、财务或合规，客户购买的不只是字段，而是：来源、更新、版本、适用范围、错误边界和出了问题后的修复能力。

### 5. 真实支付比口头承诺强

定价可以先是实验值，但必须尽早暴露真实支付摩擦。支付、账单、额度、退款和支持成本本身也是产品假设的一部分。

### 6. 复用应晚于验证

第一次遇到需求时解决问题；第二次遇到相似问题时提炼接口；第三次仍然出现时才考虑通用平台。不要为没有第二个客户的抽象提前付费。

### 7. 早期品牌和域名必须保留战略期权

在需求尚未验证前，域名不是产品定位的永久宣言，而是一个会影响未来迁移成本的架构决策。精准域名能提高第一眼理解，但也会把尚未证实的假设写进 URL、搜索索引、文章、邮件、截图和客户记忆中。

早期更重要的是保留可逆性：

- 域名表达稳定的能力层、数据层或平台层，而不是未经验证的单一垂直场景。
- 具体行业、数据集和用例放在页面标题、产品路径、API 版本或子路径中。
- 如果必须使用精准域名，应同时持有一个更宽泛的母域名，并让精准域名可以 301 到母域名下的稳定路径。
- 文章、文档、API 客户端和邮件签名优先引用可迁移的 canonical URL，而不是把项目假设写死在每个链接中。
- 域名选择要评估退出成本：文章迁移、SEO、反向链接、API Base URL、OAuth 回调、支付 Webhook、证书、客户白名单和品牌认知。

这不是鼓励模糊定位。正确做法是：对外叙事可以窄，底层入口保持宽；先用内容和落地页测试具体定位，等付费和留存证据出现后，再决定是否把场景写进品牌。

### 8. 不要把企业行动责任外包给产品

企业级方案经常要求客户老板或内部 champion 持续推动预算、跨部门协同、流程改变、数据治理、培训和结果问责。外部创业者很难替客户完成这些组织行动。

除非客户已经提供明确的预算所有者、内部 champion、决策者、试点责任人、数据权限和截止时间，否则不要把需要组织变革才能产生价值的企业方案作为 0→1 主线。优先寻找一个人或一个团队可以独立购买、使用并获得结果的工作流。

## 常见反模式

- 先做完整平台，再寻找客户。
- 把“用户说有兴趣”当成付费证据。
- 用功能数量替代价值证据。
- 用注册量和调用量掩盖没有生产使用。
- 把一次性需求包装成订阅业务。
- 在没有数据许可和质量门禁时售卖数据。
- 过早做全球覆盖、复杂权限、完整 SDK 或微服务。
- 在需求未验证前注册过窄的域名，并把文章、API、回调和客户认知全部绑定到该假设。
- 因为域名和文章已经发布，就把沉没成本误认为市场需求，继续硬撑错误方向。
- 把需要客户老板推动组织行动的企业方案，当成普通 SaaS 销售；没有内部 champion、预算和权限仍然投入长期交付。
- 只做 Delivery，不做 Discovery。
- 为了证明方向正确而回避失败证据。
- 通过低价掩盖价值不清，而不是提高确定性。
- 看到高频使用就默认会付费，跳过支付意愿和单位经济验证。
- 追逐大众日活，却没有足够获客预算、内容能力或网络效应。

## 输出模板

遇到创业问题时，优先按以下结构回答：

1. 当前阶段和核心不确定性。
2. 已知事实、推测和证据缺口。
3. 最高风险的 3 个假设。
4. 最小验证实验和强证据标准。
5. MVP 最小可信闭环。
6. 北极星指标和阶段闸门。
7. 明确的继续、转向、缩小或停止条件。
8. 本周应做的最小行动。

## 诚实边界

- 这是一套提高判断质量的框架，不是成功保证书。
- 不同市场、客单价、监管环境和销售周期会改变验证速度。
- 早期证据通常有选择偏差，付费客户也不代表 PMF。
- 北极星指标需要根据真实工作流调整，不能机械套用。
- 任何阶段都可能因为新证据而回退，不要把路线图当承诺。
