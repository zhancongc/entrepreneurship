# 产品需求验证与市场调研

> 先验证问题、买家和付费，再生成 PRD 或扩大开发。

## 核心任务

本 Skill 的默认目标不是证明用户的想法正确，而是尽快减少最贵的不确定性。每次运行必须回答：

1. 谁会购买、谁使用、谁受益、谁承担错误成本？
2. 他们最近是否为这个问题付出过时间、金钱、风险或机会成本？
3. 当前替代方案是什么，为什么还不够好？
4. 最小方案能否进入真实工作流？
5. 是否有重复触发、信任和付费的行为证据？
6. 下一步应该继续、缩小、转向、暂停还是停止？

不得默认把问题包装成机会，也不得在证据不足时输出“市场需求已验证”。

## 与 PRD 生成的关系

本 Skill 优先于 `prd-generator` 使用。正确顺序是：

```text
需求验证
-> 发现真实问题和买家
-> 取得真实样本
-> 完成最小行为实验
-> 获得付费或明确采购证据
-> 再生成 PRD
```

没有通过问题闸门和付费闸门时，只输出验证方案或实验版 MVP，不输出大而完整的功能路线图。

## 工作流

### 1. 解析需求和项目阶段

从输入中提取：

```yaml
product:
  name:
  type: software | api | data | service | marketplace | other
  proposed_solution:
stage: idea | prototype | mvp | pilot | paid | retained
buyer_hypotheses: []
user_hypotheses: []
problem_hypotheses: []
```

必须将内容分为三类：

- **事实**：已有代码、客户、付款、使用记录或可核验来源。
- **推测**：创始人或模型认为可能成立的判断。
- **未知**：必须通过客户行为或实验才能回答的问题。

如果输入不足，最多提出 3 个会改变验证路径的问题；不因缺少次要信息而停住。

### 2. 建立假设栈

至少建立以下假设，并按“如果……那么……”表达：

| 假设 | 必须验证的内容 |
|---|---|
| 问题 | 目标用户是否反复遇到真实且有代价的问题 |
| 买家 | 是否存在有预算、有权力或能推动购买的人 |
| 价值 | 解决问题的价值是否高于切换和支付成本 |
| 方案 | 最小方案是否足以完成关键任务 |
| 信任 | 用户是否敢把关键数据或决策交给该方案 |
| 频率 | 问题是日常、监控、项目、变更还是低频高风险触发 |
| 付费 | 是否有真实付款、采购流程或明确预算 |
| 渠道 | 能否以可承受成本触达相同类型买家 |
| 经济 | 数据、交付、支持、支付和获客成本后仍有利润 |

每个假设必须包含：当前证据、未知点、最小实验、强证据标准、截止日期和失败后的动作。

### 3. 选择最高风险未知数

优先验证同时满足以下条件的未知数：

- 如果为假，整个产品方向失去意义。
- 当前证据最弱。
- 可以用低成本实验快速验证。
- 结果会改变下一步决策。

默认优先级为：问题真实性 > 买家和付费 > 首次价值 > 重复使用 > 获客 > 工程扩展。

### 4. 做二手调研，但只把它当线索

可以使用 `multi-search-engine` 和 `webfetch` 调研：

- 目标公司官网、产品页、帮助中心和 API 文档。
- 客户案例、招聘信息、公开实施说明和产品更新日志。
- 竞品覆盖范围、定价、数据来源、集成方式和限制。
- 行业论坛、专业社区、公开投诉和具体工作流讨论。
- 政策、法规、数据源许可和供应商风险。

每条结论标注证据等级：

```text
A：客户公开展示真实工作流、采购、集成或结果案例
B：多个独立来源反复描述同一问题
C：单个帖子、评论或营销文案
D：行业常识、模型推断或创始人假设
```

搜索量、市场规模报告、竞品存在、落地页点击、留下邮箱和“听起来不错”不能单独证明需求或付费。

### 5. 设计一手访谈

访谈目标是还原过去发生的行为，不是征集愿望。优先找能看到流程和成本的人，再触达预算所有者。

推荐顺序：

1. 最近处理过问题的实际使用者。
2. 承担错误、延迟或客户支持成本的人。
3. 技术接入或数据采购负责人。
4. 预算批准者或内部 champion。

通用访谈问题：

```text
请讲一次最近 90 天内发生的具体事件。
当时是谁发现问题？使用了什么替代方案？
从触发到解决经过哪些步骤，花了多少人时或金钱？
哪些订单、报价、客户、系统或指标受到影响？
能否展示脱敏的工单、表格、邮件、截图或内部流程？
问题多久重复一次，什么事件会再次触发？
现在为什么继续使用现有方案，最不满意的是哪一步？
谁可以批准试点或采购，预算属于哪个部门？
能否提供一个真实样本，让我们用最小方案处理并回到你的工作流？
```

避免把以下问题当作核心证据：

```text
你觉得这个想法有价值吗？
你会不会使用？
如果有这个产品，你愿不愿意购买？
你觉得这个价格合理吗？
```

### 6. 用真实样本做最小行为实验

优先采用人工服务、限定数据集、CSV、邮件报告、可点击原型或单端点 API。实验验证价值，不验证代码数量。

通用闭环：

```text
客户提供真实输入
-> 交付最小结果
-> 客户放回报价、审核、监控或其他生产流程
-> 观察是否采取行动或再次请求
-> 提出付费试点
```

数据或规则产品至少记录：输入、来源、版本、更新时间、覆盖状态、错误边界、人工处理时间和客户实际使用位置。

### 7. 验证付费和交付形态

行为证据强度从高到低：

```text
真实付款
> 已签试点或明确采购流程
> 有预算、负责人、技术评审和上线日期
> 提交真实样本并完成接入
> 重复使用结果
> 愿意访谈或留下联系方式
> 口头表示感兴趣
```

客户有问题不等于客户需要 API。若客户愿意付费但不愿接 API，应测试 CSV、规则变化邮件、人工核验、插件、咨询交付或数据文件等形态。

提出付费试点时必须写清：客户对象、真实范围、交付结果、周期、价格、支持边界、数据责任和下一步采购条件。避免只问“愿不愿意付费”。

### 8. 输出决策报告

输出必须包含：

```markdown
# 产品需求验证报告

## 1. 执行摘要
## 2. 当前阶段和最高风险未知数
## 3. 已知事实、推测和证据缺口
## 4. 买家、使用者、受益者和风险承担者
## 5. 假设栈与证据等级
## 6. 当前工作流和替代方案
## 7. 二手调研线索
## 8. 访谈设计或访谈记录汇总
## 9. 行为实验设计与结果
## 10. 付费和交付形态验证
## 11. 假设状态：已验证 / 部分验证 / 未验证 / 证伪
## 12. MVP 最小可信闭环
## 13. In scope / Out of scope
## 14. 继续、缩小、转向、暂停或停止建议
## 15. 下一周期行动、负责人、截止日期和通过标准
```

每个结论必须能追溯到访谈记录、客户行为、公开来源或明确标注的推测。存在冲突证据时同时呈现，不用平均数掩盖分歧。

## 证据评分与决策模型

可以对候选需求打分，但分数表示“当前证据支持程度”，不是市场规模、成功概率或财务预测。没有证据的维度必须标记为 `N/A` 或“未验证”，不能默认给中间分。

### 评分维度

每个维度使用 0–5 分，并记录 `score`、`confidence`、`evidence_count` 和 `evidence_ids`：

| 维度 | 权重 | 5 分标准 |
|---|---:|---|
| 问题强度 | 25% | 多个目标客户有近期、具体且昂贵的问题，并展示当前处理材料 |
| 重复触发 | 15% | 有明确的日常、每周、项目或政策变化触发，且客户会再次处理 |
| 付费意愿 | 20% | 已付款，或有预算、采购负责人、采购流程和明确日期 |
| 价值可验证性 | 15% | 客户能用结果完成真实报价、审核、监控或其他关键任务 |
| 信任与数据可交付性 | 10% | 来源、质量、权限、更新和责任边界可说明，客户愿意用于生产 |
| 获客可行性 | 10% | 能通过可承受成本触达明确客户，且已有有效渠道或转介绍 |
| 单位经济 | 5% | 价格覆盖数据、交付、支持、支付和获客成本，并有合理毛利 |

总分计算：

```text
总分 = Σ(维度得分 / 5 × 维度权重)
```

结果保留整数百分比，但不得输出超过当前证据精度的结论。例如只有 3 场访谈时，可以输出“当前证据分 62/100”，不能输出“成功概率 62%”。

### 证据置信度

每个维度还要单独计算置信度，防止高分建立在少量口头意见上：

| 置信度 | 适用条件 |
|---|---|
| 高 | 至少 3 个独立目标客户，且至少 1 个有真实行为、材料、接入或付款证据 |
| 中 | 至少 2 个相关来源，包含具体案例，但缺少付款或生产使用 |
| 低 | 单一访谈、公开推测、营销文案或没有目标客户身份的反馈 |
| 未知 | 没有直接证据 |

推荐记录格式：

```yaml
dimension: willingness_to_pay
score: 3
weight: 0.20
weighted_score: 12
confidence: medium
evidence_count: 4
evidence_ids: [E-003, E-007, E-009, E-011]
why_not_higher: "有真实样本和采购负责人，但尚未支付试点费用"
next_test: "提交 4 周付费试点报价并确认采购日期"
```

### 决策分层

评分不能绕过硬门槛。先检查硬门槛，再看总分：

| 结果 | 条件 | 建议动作 |
|---|---|---|
| 做 | 总分 ≥ 70，问题强度 ≥ 3，付费意愿 ≥ 3，至少 1 个真实行为证据，且没有关键维度未知 | 做窄 MVP 或付费试点 |
| 小范围验证 | 总分 50–69，或总分 ≥ 70 但付费、信任或价值验证不足 | 停止扩展开发，继续访谈和人工实验 |
| 转向 | 总分 < 50，但某一细分场景问题强度 ≥ 4 或已有付费替代方案 | 换买家、场景、交付形态或价值主张 |
| 暂停/不做 | 问题强度 < 3，且没有具体行为证据；或连续实验无人提供真实样本 | 暂停投入，不用功能扩展掩盖需求不足 |

以下情况直接阻止输出“可以做”：

- 付费意愿为未知，且没有客户愿意进入付费试点或采购流程。
- 问题强度低于 3，即使市场规模或竞品数量很大。
- 关键数据、许可或责任边界不可控。
- 价值只能通过长期组织变革实现，但没有内部 champion、预算所有者和截止日期。

### 需求比较矩阵

当用户比较多个方向时，使用同一套维度、权重、样本标准和时间窗口，不得为偏好的方向调整权重：

| 候选需求 | 问题 25 | 触发 15 | 付费 20 | 价值 15 | 信任 10 | 获客 10 | 经济 5 | 总分 | 置信度 | 决策 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---|---|
| 方向 A |  |  |  |  |  |  |  |  |  |  |
| 方向 B |  |  |  |  |  |  |  |  |  |  |

比较报告必须同时展示：

- 各方向使用了多少有效样本。
- 哪些分数来自客户行为，哪些来自公开资料或推测。
- 分数差异是否大于证据误差。
- 哪个未知数最可能改变排序。
- 下一步只验证哪一个未知数，而不是同时开发所有方向。

### 示例：当前贸易数据产品

以下只是评分格式示例，不是已经完成的市场结论：

| 维度 | 示例分数 | 当前理由 |
|---|---:|---|
| 问题强度 | 0 | 尚无目标客户访谈证据，不能因为规则复杂就给分 |
| 重复触发 | 0 | 尚未知道是日常查询、政策变化还是一次性项目 |
| 付费意愿 | 0 | 没有付款或采购证据 |
| 价值可验证性 | 1 | 已有可演示 API，但尚未进入客户真实工作流 |
| 信任与数据可交付性 | 2 | 已有来源和版本设计，但许可、覆盖和生产质量仍需验证 |
| 获客可行性 | 1 | 目标客户可列出，但尚未验证触达和转化 |
| 单位经济 | 0 | 没有真实交付成本、价格和支持成本 |
| 当前结论 | - | 不能判断“可做”，下一步先验证问题和付费 |

技术完成度不能替代需求证据。实际运行时必须用真实 `evidence_id` 替换示例，并保留评分变更记录。

### 评分记录与更新规则

- 每次访谈、实验、付款或采购进展都新增证据记录，不覆盖旧分数。
- 只有新证据改变维度判断时才更新分数，并说明原因。
- 记录评分日期、样本窗口和评分人。
- 目标客户数量太少时优先展示区间或置信度，不制造小数点精度。
- 分数上升不代表 PMF；真实付款、重复使用和可重复获客仍需分别通过阶段闸门。

## 默认阶段闸门

根据项目规模调整数量，但不能降低证据类型要求。

### 问题闸门

- 至少 10 场有效访谈，或较小市场中覆盖主要目标客户类型。
- 多数受访者能讲出最近的具体案例，而不是泛泛同意。
- 至少数个客户能展示当前流程或脱敏材料。
- 至少数个客户能量化时间、错误、延迟、风险或支持成本。

### 价值闸门

- 至少 3 组真实样本完成处理和复核。
- 至少 2 家把结果放入真实业务流程。
- 至少 2 家提出再次查询、监控或扩展的触发条件。

### 付费闸门

- 至少 1 家真实付款，或进入有负责人、预算和截止日期的采购流程。
- “免费试用”“发资料看看”“以后有需要联系”不算通过。

### 产品化闸门

- 不同客户反复需要相同输入、输出、更新和支持边界。
- 手工交付成本、数据许可和错误责任可控。
- 只有满足以上条件，才建议投入完整 API、自动化、套餐和全球覆盖。

## 针对数据、规则和合规类产品的额外要求

客户购买的不只是字段，还包括来源、更新、版本、适用范围、覆盖边界、错误修复和责任边界。调研必须单独验证：

- 客户是否有权使用和再分发相关数据。
- 数据错误由谁发现、谁修复、谁承担后果。
- 官方原文、机器翻译和业务判断是否被混为一谈。
- 客户要的是查询、变更监控、批量文件、人工核验还是最终决策。
- 低频高风险场景是否比低价高频 API 更适合该市场。

## 反自欺规则

- 不得虚构访谈、客户原话、市场数据、价格或竞争格局。
- 无法访问某个渠道时，明确标记为未调研，不用推测补齐。
- 公开调研只能支持线索，不能替代一手行为证据。
- 竞品存在不等于新产品有空间；竞品缺失也不等于需求不存在。
- 没有真实付款或明确采购动作，不得称为商业模式已验证。
- 没有重复使用证据，不得称为留存或持续需求已验证。
- 不因已有代码、域名、文章或沉没成本而降低阶段闸门。
- 没有通过问题和付费闸门时，不扩大市场范围、不优先开发更多功能。

## 工具协作

```text
multi-search-engine -> 公开线索、客户名单、竞品和行业讨论
webfetch -> 官网、文档、案例和公开帮助中心
entrepreneurship-operating-system -> 假设、实验、指标和阶段闸门
prd-generator -> 仅在需求验证通过后生成 PRD
feishu-doc -> 调研完成后发布报告（用户明确要求时）
```

## 诚实边界

这是一套提高判断质量的验证协议，不是市场成功保证。公开资料存在选择偏差，访谈存在样本偏差，少量付费客户也不代表 PMF。所有结论都应保留证据来源、适用范围和失效条件。
